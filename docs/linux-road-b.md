# Дорога B: нативная сборка SimInTech под Linux

Документ отвечает на вопрос «что из нашего набора инструментов выражается без
COM». Это инвентаризация перед проектированием, а не отчёт о сделанном: кода
здесь нет.

## Что установлено фактами

**Нативная сборка существует.** `mmain` под Linux — ELF 64-bit, Free Pascal,
собранный из той же Delphi-кодовой базы. В исходниках поставки ей соответствует
отдельное дерево (`source/linuxroot/`) с FPC-шимами, а не `source/exe/`, где
лежит COM-спецификация.

**COM в ней нет.** `IMVTU_Server`, `MVTU_Server`, CLSID сервера,
`CoCreateInstance`, `regserver` — ноль вхождений. Наш сервер на этой сборке
запустить нельзя: он весь построен вокруг COM-клиента.

**Что в ней есть:**

- командная строка (`silentmode`, `runstep`, `setparameter`, `exitonstop`,
  `macros` — те же опции, что у Windows-сборки);
- встроенный язык (создание блоков и связей, обход портов, топология —
  `createblock`, `createwire`, `traceallports`, `getportwireid`);
- плагинный ABI (`DllInfo`, `ProcessCommand`, `CreateObject`) и около 125
  плагинов `.so` — включая Python, Modbus, OPC UA, COMTRADE, веб-сервер и
  библиотеку кодогенерации.

## Инвентаризация: что выражается, а что нет

Опора — наш собственный набор инструментов. «Выражается» означает: результат
достижим на нативной сборке без COM — командной строкой, скриптом на встроенном
языке или чтением файлов.

| Инструмент | Дорога B | Чем |
|---|---|---|
| `open_project`, `save_project` | частично | CLI открывает и сохраняет проект; управлять форматом и содержимым так нельзя |
| `create_project` (из шаблона) | частично | открытие файла проекта есть; настройка времени расчёта — только параметром/скриптом |
| `run`, `step`, `stop` | да | `/run`, `/runstep`, `/stop`, `/exitonstop` |
| `get_time` | скриптом | модельное время доступно встроенному языку; CLI его не печатает |
| `add_block`, `set_block_param`, `get_block_params` | **скриптом**, не CLI | `createblock` и свойства объекта есть в языке; перечисления свойств нет и там — каталог нужен по-прежнему |
| `connect` | **скриптом** | `createwire` в языке есть; командной строке недоступно |
| `list_blocks` | скриптом | обход объектов страницы |
| `list_wires`, концы линий | скриптом | `traceallports`/`getportwireid` — то, чего не даёт COM (см. Н3) |
| `list_signals`, `get_signal`, `set_signal` | нет | обмен идёт через `TDataDescriptor`, а это COM-понятие |
| `export_signal_db` | скриптом | макрос `dbexporttoxml`, затем разбор XML — он и так без COM |
| `read_output_file`, `summarize_output_file` | да | чистое чтение файлов, работает и сейчас |
| `inspect_project_file` | да | разбор `.xprt` — уже без COM |
| `layout_place` | да (частично) | координаты считаем мы; применить их можно скриптом |
| каталог блоков, реестр функций языка | да | чтение файлов поставки |
| `project_network_role` | да | чтение `.dblocalconf` |

**Не выражается ничего COM-специфичного:** `SetBlockProp` и `GetBlockPropAsString`
(свойства объекта в языке есть, но их перечисления — нет), сигналы по
`TDataDescriptor`, `CreateWire` как метод интерфейса. Это и есть граница дороги
B.

## Что это значит для проектирования

1. **Дорогу B нельзя сделать «тем же сервером, но на Linux».** COM — не
   транспорт под нашим кодом, а сам код: `core/` построен на идентификаторах,
   которые выдаёт сервер.
2. **Общая часть — не сервер, а разбор.** Каталог, реестр языка, читатели
   `.tbl`/`.pak`/`.dblconf`, разбор `.xprt`, сводки по файлам результатов уже
   работают без COM и переиспользуются дорогой B целиком. Это самая большая
   часть нашей работы, и она не пропадёт.
3. **Мост между дорогами — скрипт и файл.** Единственный способ управлять
   моделью без COM — встроенный язык; значит, контракт адаптера: «сгенерировать
   скрипт → выполнить → прочитать результат из файла». Никаких идентификаторов
   наружу.
4. **Контракт отказа другой.** У COM-пути отказ — `isError` с причиной от
   сервера; у дороги B причина будет от CLI (код возврата и текст в cp1251) или
   от скрипта. Смешивать их в одном слое нельзя: клиент не отличит «модель не
   посчиталась» от «мы не смогли запустить».

## Что нужно сделать, чтобы двигаться дальше

Не код, а ответы на три вопроса:

1. **Доступна ли нативная сборка нам** — то есть можно ли её запускать в нашей
   среде (лицензия, зависимости, плагины). Без этого проектировать нечего.
2. **Отдаёт ли встроенный язык результат наружу** — файл, сигнал или код
   возврата. От этого зависит, будет ли мост вообще.
3. **Как выглядит отказ** на нативной сборке: коды возврата CLI и текст ошибок
   встроенного языка.

До ответов на них писать адаптер — значит писать код под неизвестный контракт.
