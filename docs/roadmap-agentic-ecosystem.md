## 3. Главная находка: каталог параметров — не «этап 2», а блокер этапа 1

**В COM API нет метода перечисления свойств блока.** Проверено по карте методов
(`com_api_inventory.md`): существуют только `GetBlockPropAsString(BlockId, PropName)`,
`SetBlockProp(BlockId, PropName, StrValue)` и `GetPropHandle(BlockId, PropName)` —
все требуют **знать имя свойства заранее**. Аналогов `GetPropCount`/`GetPropName` нет.

Следствие: `get_block_params` невозможно реализовать «чтением всех свойств».
Имена должны приходить из внешнего каталога — то есть из работ, которые исходный
план относил к **Этапу 2** (`simintech-library-curation`).

**Вывод: Этап 2 в части каталога — предварительное условие для завершения Этапа 1,
а не следующий шаг.** Исходный порядок этапов нужно инвертировать.

### 3.0. Проверено на реальном SimInTech (2026-09-10)

Генератор прогнан на `C:\SimInTech64` под Windows. Результаты:

1. **Параметры блока лежат в `<custom_props>`, а не в `<visual_props>`.**
   Исходная схема §3.2 была неверна. `visual_props` — это оформление
   (`Color`, `Points`, `LabelFont`, ...), параметров расчёта там нет.
   Парсер, читавший `visual_props`, давал **пустой каталог** без единой ошибки.

2. **`.xprt` пишется в UTF-8 с BOM, а не в cp1251.** `xprt_signals.py` и первая
   версия генератора читали его как cp1251; русские имена классов превращались
   в мусор, и фильтр отбрасывал все классы. cp1251 декодирует любые байты,
   поэтому ошибки не возникало.

3. **Сгенерированы 12 классов из 14.** Две записи — «Выход данных состояния»
   и «Состояние автомата» — тогда сочли через COM неcоздаваемыми и отнесли к
   `UNSUPPORTED_COM_BLOCK_CLASSES`. **Опровергнуто позже (2026-09-15):** они
   создаются, но по **полному имени записи** — «Конечные автоматы - Состояние
   автомата»; короткий заголовок с палитры `CreateBlock` не принимает. Обе
   записи есть в каталоге (958 классов), а `UNSUPPORTED_COM_BLOCK_CLASSES`
   содержит другие две — «Из памяти» и «Порт выхода». См. §9.2.

4. **Вычисляемые параметры** (`mode 0`) отделяются от задаваемых (`mode 1`).
   Например, у «Усилителя» `formula_visible` — вычисляемый.

### 3.1. Ошибки в именах параметров были и в примерах

Засев каталога вручную из `examples/` оказался **сам по себе ошибкой**: имена
в примерах частично неверны. Проверка на реальном SimInTech:

| Утверждение | Реальность |
|---|---|
| «Константа»: `y0` | параметр называется **`a`** (`y0` не существует) |
| «Сумматор»: `xn` | параметра нет; число входов задаётся длиной `a` |
| «Ступенька»: `y0` | верно (`t`, `y0`, `yk`) |
| «Интегратор»: `k`, `x0` | верно |

Проверено записью и последующим чтением `.xprt`:

| Что делали | Значение `a` у «Константы» в результате |
|---|---|
| `set_property("a", 5.0)` | `[5]` — применилось |
| `set_property("y0", 5.0)` | `[1]` — **не применилось, без ошибки** |

**Следствие:** `examples/pid_controller.py` и `tests/integration/test_lifecycle.py`
строили модель с неверной уставкой (константа оставалась дефолтной). Исправлено
2026-09-10 — заменено на `a`.

Ошибка подтверждает главный тезис: **каталог нельзя писать вручную**, включая
копирование имён из примеров.

### 3.2. Как каталог генерируется (реализовано)

```bash
# Полный обход: Windows + mmain.exe /regserver, живёт в simintech-code.
simintech-generate-catalog --bin-dir <bin> --profile <base.xml> \
    --dump <dump.xprt> --out <catalog.json> [--merge]
# Разбор готовой выгрузки — COM не нужен, работает и на Linux:
simintech-generate-catalog --xprt <dump.xprt> --out <catalog.json>
# Доля классов, для которых имена проверяются (критерий, а не оценка):
simintech-generate-catalog --coverage
```

**Без `--out` генератор пишет в `data/block_catalog.json`, а без `--bin-dir`
обходит только `SUPPORTED_COM_BLOCK_CLASSES`** — то есть поставляемый каталог
на 958 классов затирается огрызком из тринадцати, с кодом возврата 0. Полный
обход без `--bin-dir` не запускать.

Генератор — entry point пакета `simintech-code` (раньше
`scripts/generate_block_catalog.py`). Он создаёт по блоку каждого класса из
`SUPPORTED_COM_BLOCK_CLASSES`, экспортирует проект в `.xprt` и разбирает секцию
**`<custom_props>`** каждого объекта: имя, значение по умолчанию и `mode`
(1 — задаваемый, 0 — вычисляемый). Результат —
`simintech_api/data/block_catalog.json` в `simintech-code`.

Справочник блоков (`blocks/` в `simintech-code`) как источник имён
**непригоден**: там используются читаемые имена (`signs`, `numInputs`, `num`,
`den`, `reset`), которых в SimInTech нет.

## 4. Дефекты текущего кода (не новые функции)

Исходный план подаёт изоляцию stdout как ключевое решение. Проверено
экспериментально (см. ниже) — это **страховка, а не починка**.

1. **Изоляция stdout.** Проверено запуском сервера как подпроцесса с настоящим
   JSON-RPC-хендшейком:

   | Конфигурация | Валидных JSON-RPC в stdout | Мусорных строк |
   |---|---|---|
   | Без изоляции | 2 | 0 |
   | С изоляцией | 2 | 0 |

   Вывод: FastMCP пишет баннер в stderr сам, а в MCP-пути сейчас нет кода,
   печатающего в stdout. **Активного дефекта нет.**

   Но риск реален и отложен: `PipeLogger` по умолчанию печатает в stdout
   (`utils/logger.py:34`) и пока нигде не подключён. Его подключение к MCP-пути
   сломает JSON-RPC — причём молча. Поэтому защита добавлена заранее
   (`_StdoutGuard` в `server.py`): она отводит `write()` в stderr, оставляя
   `.buffer` настоящим — именно через него транспорт пишет протокол.

   Ограничение: не перехватывает запись напрямую в дескриптор 1 из нативного
   кода. Для SimInTech это неактуально: `mmain.exe` — out-of-proc COM-сервер
   со своей консолью.

2. **`fastmcp` не объявлен** в `pyproject.toml` (там только `mcp>=1.0.0`).
   Чистая установка → падение `simintech-mcp` на импорте `from fastmcp import
   FastMCP`. Для публикации (Этап 3) это стоп-фактор. Тесты используют
   `@pytest.mark.anyio`; маркер регистрирует плагин, **встроенный в `anyio`** —
   пакет `pytest-anyio` не нужен (это заглушка с текстом «You don't need this
   package»), в зависимости добавлен `anyio`.

### 6.1. Дефекты, найденные при проверке MCP-сервера на реальном COM

Проверка инструментов через stdio-транспорт на Windows вскрыла три дефекта,
которых не видно ни в unit-тестах, ни на Linux:

1. **Сервер не работал с COM вообще.** COM привязан к потоку, а FastMCP
   выполняет синхронные инструменты в пуле потоков: `CoInitialize` там не
   вызывался (`CO_E_NOTINITIALIZED`). Исправлено — `COMClient.connect()`
   инициализирует COM для текущего потока.
2. **Клиент использовался из разных потоков.** Пул чередует потоки, а COM-объект
   из чужого потока даёт `CO_E_OBJNOTCONNECTED`. Исправлено — все COM-вызовы
   идут через один выделенный поток (`_com_threaded`).
3. **`SetBlockProp("Name", ...)` не переименовывает блок.** Имя остаётся
   автоматическим (`k_0`) и в `get_name()`, и в `.xprt`; `BlockAfterEdit` не
   помогает, отдельного метода в COM API нет. `add_block` теперь сообщает об
   этом явно — иначе `connect` по имени молча не находил бы блок.

Дополнительно: `Block.class_name` брал имя из `GetBlockPluginName`
(внутреннее `TMBTYBlock`), из-за чего `get_block_params` не сопоставлял класс
с каталогом. Теперь читается свойство `ClassName` («Константа»).

Эти дефекты означают, что заявленная в §1 готовность Этапа 1 была формальной:
код существовал, но на Windows не работал.

### 6.3. Почему сигналы не читались — две независимые причины

Разобрано и **устранено** 2026-09-10 на реальном SimInTech.

**Причина 1: у проекта нет базы сигналов.** Обмен идёт через список сигналов
проекта и подключённую базу. У проекта из `Project.new()` нет ни того, ни
другого: `GetProjectDB` → `(None, None)`, `GetProjectSignalList` → список
длиной 0 даже при добавленном блоке «Выход алгоритма». Выход блока не является
элементом данных, поэтому `FindSignalData` по именам блоков не находит ничего.
Это не дефект, а свойство: читать можно только сигналы базы.

**Причина 2 (наш дефект, и главный): подмена класса дескриптора.** Даже у
проекта **с базой** чтение не работало. `_to_descriptor` оборачивал дескриптор,
сгенерированный comtypes из библиотеки типов, в наш одноимённый
`TDataDescriptor`. comtypes принимает только свой тип и падает с
«expected TDataDescriptor instance instead of TDataDescriptor». Проверено
напрямую: с родным дескриптором `ReadAsFloat` возвращает значение, с
подменённым — ошибку. `isinstance` подмену не ловит: классы одноимённые, но
разные.

Дополнительно: XML-заглушка `list_signals()` возвращала имена блоков, выдавая
их за сигналы, — из-за этого ошибка всплывала позже и в другом месте.

Проверены и отвергнуты: состояние проекта (`SetCurrentPage`, `BlockAfterEdit`,
`InitBlock`, `ProjectStart`) на результат не влияет; `ExportDBAsXML` в
интерфейсе нет (верное имя — `ExportDBToXML`).

**Исправлено:**

- `_to_descriptor` пропускает родной дескриптор насквозь (`is_descriptor`,
  `descriptor_is_valid` — проверка по атрибутам, а не по типу);
- `SignalInfo` получил `source` (`com`/`xml`) и `readable`; имена из XML
  помечены как нечитаемые;

  читаемые сигналы и имена блоков.

**Проверено на `sar/SAR/2.1.regulator.prt`** (реальный проект с базой
`signals.db`), в том числе через MCP:

### 6.5. Создание проекта с нуля, расчёт и вывод результата в файл (решено)

Причина, по которой проект из `Project.new()` не считал, найдена 2026-09-15
разбором экспорта `.xprt`. У пустого проекта **один слой «Нулевой слой»** с
пустыми `<groups>`/`<pluginname>` и пустой секцией `<parameters>`. У
работоспособного проекта слой — «Автоматика» с плагином
`$(Root)\mbtylib.dll@layer`, а в `<parameters>` лежат настройки расчёта
(`starttime`, `endtime`, `hmin`, `hmax`, `intmet`, …). То есть `NewProject`
даёт проект без расчётного слоя: считать в нём нечему, но и ошибки нет.

**Рабочий цикл (проверен через MCP по stdio):**

```
create_project(end_time=1.0)          # OpenTemplate + SetLayerProp endtime
add_block("Константа", props="a=2")   # → k_0
add_block("Усилитель", props="a=3")   # → kx_0
add_block("В файл", props="filename=C:\\Temp\\out.txt,count=1,step=[0.2]")
connect(k_0, kx_0) → connect(kx_0, ToFile_0)
run(to_time=1.0)                      # время доходит до 1.0
read_output_file("C:\\Temp\\out.txt") # 6 строк: 0 … 1, значение 6 (2×3)
```

**Что для этого добавлено:**

| Слой | Что |
|---|---|
| `simintech-code` | `Project.from_template()`, `find_model_template()`, `COMClient.open_template()` / `set_layer_prop()`, `Project.set_calc_end_time()`, блок «В файл» в `SUPPORTED_COM_BLOCK_CLASSES`, §18 в карте COM API |
| `simintech-mcp` | `create_project(end_time=…)` (из шаблона), `set_calc_time(seconds)`, `read_output_file(path)` |
| `simintech-skill` | скилл `simintech-simulation`: порядок «собрать → задать время → запустить → прочитать файл» |

Ограничения, которые остаются: блок «В файл» пишет **числа** (массивы и
структуры — нет), а шаг записи `step` задаётся массивом и не привязан к шагу
интегрирования. `get_signal` по-прежнему требует проекта с подключённой базой
сигналов.

**Побочная находка: неподключённый вход молча останавливает расчёт.** Если у
блока вход ни с чем не соединён, `GetProjectTime` остаётся `0.0` и ошибки не
выдаётся. Проверено на одной и той же схеме: «Константа → В файл» со связью
считает до `1.0`; та же схема с висящим входом у «В файл» — `0.0`; одна
«Константа» без «В файл» — снова `1.0`. Первый прогон E2E упал именно на этом
(блок «В файл» был создан, но не соединён). Поэтому `run` в сообщении о неудаче
перечисляет обе причины: неподключённый вход и отсутствие расчётного слоя.

### Обновление 2026-09-22: топология в `simintech-code` и связанные работы

В `simintech-code` влит PR #13 (`ed4fe130`): библиотека получила публичный
`read_topology()`, который через `ScriptBridge` читает объекты, порты и связи
текущего контейнера. В MCP этот API пока **не выведен и не используется**;
`simintech-mcp` остаётся на ранее закреплённом commit `13415c5`.

При реализации топологии подтверждены и зафиксированы четыре работы. **Первая
закрыта, три остаются** отдельным контуром:

1. **Потеря скрипта неглавной страницы — исправлено в `simintech-code` PR #15.**
   `ScriptBridge` теперь определяет изменённую запись по уникальной метке и
   возвращает исходный скрипт в ту же текущую COM-страницу; живой red→green
   прогон подтвердил сохранение 939-символьного скрипта `acrms_Circuit1` при
   сохранении результата топологии 35/64/32. Остаточное допущение «запись
   выгрузки ↔ та же страница» измерено на одной поставке и должно быть
   проверено на дополнительных моделях до вывода topology в MCP.
2. **Отсутствие `ProjectStop` после probe — закрыто в `simintech-code`
   (ветка `feat/bridge-lifecycle`).** Расследование оказалось содержательнее
   исходной формулировки: «зависание ~150 с» — это не таймаут и не медленный
   расчёт, а **модальное окно** «Установка блока на схему в процессе
   моделирования запрещена», которое внешний COM-клиент снять не может, и
   вызов стоит, пока окно не закроет человек. `run_probe` оставлял проект
   инициализированным (`GetProjectStateFlag = 7`), а в этом состоянии среда
   отвергает добавление блока. Теперь мост останавливает расчёт на каждом пути,
   где его запускал, и **подтверждает** остановку чтением флага. Замеры,
   контракт, red→green и мутации — в
   `simintech-code/docs/superpowers/specs/2026-09-22-script-bridge-lifecycle-design.md`.
   Проба также **отказывает**, если проект не остановлен, — иначе она
   уничтожила бы расчёт (`ProjectStart` — это инициализация, модельное время
   сбрасывается). Состояние при этом называется прямо: `0` остановлен, `1`
   инициализирован, `3` идёт расчёт, `7` пауза — «не остановлен» и «идёт
   расчёт» не одно и то же, и агент по тексту обязан их различать.

   **Следствие для MCP, которое надо учесть при выводе топологии:** сценарий
   «`run`, затем `read_topology`» без явной остановки расчёта больше не
   работает. Отказ `ScriptBridgeUnsafeStateError` обязан переводиться в
   понятное агенту сообщение, а не выглядеть поломкой инструмента. Заодно это
   повод решить, не должен ли сам MCP-инструмент чтения топологии останавливать
   расчёт — с явным предупреждением, а не молча.
3. **Три пути выхода `run_probe` минуют иерархию ошибок моста** — найдено при
   том же расследовании и намеренно не смешано с пунктом 2:
   `GetCurentPage`, снимок «до» и проверка пути результата стоят вне `try`,
   поэтому наружу уходят сырые `ComCallError` / `ValueError` вместо ошибок
   `ScriptBridgeError`. Данным это не грозит (расчёт на этих путях не
   запускается), но вызывающий — включая MCP-слой — не может отличить отказ
   моста от отказа среды по типу.
4. **`port_idx` против `getportindex(peer)` — закрыто в `simintech-code`
   (PR #18).** Тождество доказано двумя независимыми способами: вендорская
   справка даёт обратный переход **примером** (`getblockportid(macro2, 2)` →
   `getportindex` → `2`), а новый живой тест
   `test_port_index_round_trip_is_identity` измеряет его на построенной модели
   («Сумматор» с тремя входами, перебор `i = 0…3`) — совпало на всех портах.

   **И там же измерена граница, которой в пункте не было.** Вне фильтра типов
   100/102 тождество **не** выполняется: на объекте линии для одного и того же
   номера `getportindex` вернул `2`, `3` и `0`. Линии в топологию не попадают,
   поэтому дефектом это не является — но означает, что фильтр типов держит не
   только состав объектов, но и достоверность адресации портов. При расширении
   охвата (пункт 5) это придётся учитывать.

   **Уточнение имени (2026-09-23, замер):** `MBTYWire` — это **имя объекта**, а
   не класс. Класс типа 101 — «Математическая»; в демо вендора 28 объектов этого
   класса. Ранее и здесь, и в отчётах он назывался «объектом линии (`MBTYWire`)»,
   что неточно.

   **Следствие для порядка работ:** препятствие к выводу топологии наружу,
   которое здесь называлось главным риском достоверности графа, снято.
5. **Экзотические типы объектов.** Фильтр топологии по типам 100/102 исключает
   часть реальных моделирующих блоков; типы 104 и 106 подтверждены живьём как
   исключённые, 105/109/113 пока только предполагаются. Расширение охвата
   требует отдельных живых экспериментов и не должно делаться догадкой.

   **Критерий для каждого нового типа (уточнён 2026-09-23).** После замера из
   пункта 4 расширение нельзя читать как «добавить классы в фильтр». Порядок
   для типа-кандидата: **обнаружение объектов → обнаружение портов → нумерация
   портов → семантика связей**, и на каждом шаге отдельное доказательство, что
   адресация совместима с текущим протоколом. Основание — граница из пункта 4:
   вне фильтра 100/102 тождество «номер порта ↔ `getportindex`» **не**
   выполняется, то есть фильтр держит не только состав объектов, но и
   достоверность адресации.

   **Контрольный тип — 101, класс «Математическая».** Объект этого типа не
   моделирующий блок и в топологию не попадает, но именно на нём измерено, что
   закон, верный для типов 100/102, не обобщается на все записи объекта. Любое
   расширение фильтра обязано сначала объяснить, почему новый тип ведёт себя как
   100/102, а не как 101.

   **Перепись типов на реальной модели (2026-09-23).** Внутри контейнера демо
   вендора — **68 объектов четырёх типов**:

   | тип | что это | объектов |
   |---|---|---|
   | 100 | модельные блоки: «Константа», «Комментарий» | 2 |
   | 101 | **связи**: «Электрическая» ×28, «Математическая связь» ×4 | 32 |
   | 102 | модельные блоки и контейнеры: «Субмодель» ×11, «СПТ - Узел» ×9, «Кнопка», … | 33 |
   | 108 | подпись, `constLabel` | 1 |

   Отсюда видно, **что фильтр 100/102 означает по смыслу**: «модельные блоки».
   101 исключён потому, что это **линия**, 108 — потому что это **подпись**, а
   не потому, что типы «неизвестны». Сходится с эталоном вендора: 2 + 33 = 35
   объектов, а 32 линии отсеяны — ровно столько же уникальных связей в эталоне.

   **Формулировка, которой этот фильтр стоит называть.** Не «известные хорошие
   типы» — это обещало бы больше, чем доказано. Точнее: **доказанный текущий
   набор типов модельных сущностей, для которых одновременно подтверждена
   совместимость существующего протокола топологии** — обнаружение, порты,
   нумерация и представление связи. Разница практическая: «хорошие типы» звучит
   как свойство типа, а на деле это свойство **пары** «тип + версия протокола», и
   расширение протокола (например, добавление provenance) может потребовать
   перепроверки уже включённых типов.

   Практический вывод для критерия: у типа-кандидата первым вопросом идёт не
   «есть ли у него порты», а **«что это за сущность»** — блок, связь или
   оформление. Порты есть и у линий (32 объекта типа 101 — все с двумя), так
   что один лишь `getblockportcount` кандидата не выделяет.

   **Оговорка:** это одна модель и один контейнер. Типов 104/105/106/109/113 в
   ней нет, поэтому перепись их не подтверждает и не опровергает — она даёт
   baseline для критерия, а не закрывает пункт. Следующий шаг — та же перепись
   на моделях, где эти типы встречаются.

   **Классы-кандидаты и их типы — замер (2026-09-23).** Собранная модель
   «Ступенька» → «В память» → «Временной график»:

   | тип | портов | класс | имя объекта |
   |---|---|---|---|
   | 100 | 1 | Ступенька | `Step_source_1` |
   | **104** | 1 | **В память** | `ToMem_0` |
   | **106** | 1 | **Временной график** | `TimeGraphic_0` |
   | 101 | 2 | **Математическая** | `MBTYWire` |

   Что из этого следует по шагам критерия:

   * **104 и 106 подтверждены замером**, оба создаются через COM и оба имеют
     порт. По первым двум шагам (классификация сущности, пригодность как
     `ObjectRow`) это кандидаты, а не исключения — но порты, нумерация и
     семантика связей у них ещё не проверялись.
   * **109 и 113 пока только имена.** Классов «Блок со встроенным
     интерпретатором» и «Блок-узел» нет среди 958 классов каталога, и
     `CreateBlock` эти имена не принимает. Это **не** опровергает их
     существование — имена могли прийти из вендорского определения модели, — но
     означает, что путь «взять класс из каталога и создать» для них не работает
     и нужен другой источник.
   * **105 («Из памяти») отказывает библиотека, а не COM.** Класс технически
     создаётся (замер 2026-09-18), запрет — в `UNSUPPORTED_COM_BLOCK_CLASSES` по
     причине неподтверждённой пригодности. Здесь подтверждается предупреждение
     «unsupported library ≠ unsupported topology»: объект для исследования
     добывается встроенным языком, и запрет библиотеки его не отменяет.

   **Попутно — второе подтверждение дефекта из пункта 6.** Модель из «В память»
   и «Временного графика» со свободными входами не считалась, и мост сообщил
   «скрипт не скомпилировался» при синтаксически верном скрипте. Второй случай
   получен **не на пробе топологии**, а на карте типов — то есть дефект не
   связан с конкретным потребителем моста.

   **Кандидаты 104 и 106: шаги протокола пройдены (замер 2026-09-23).** На той
   же модели прогнаны шаги, которые прошёл «Сумматор» — нумерация портов и
   достижимость соседа:

   | тип | объект | порт | `getportindex` | провод | соседи по `traceallports` |
   |---|---|---|---|---|---|
   | 104 | `ToMem_0` | 0 | 0 | есть | `Step_source_1` (100, порт 0), `TimeGraphic_0` (106, порт 0) |
   | 106 | `TimeGraphic_0` | 0 | 0 | есть | `Step_source_1` (100, порт 0) |

   Для обоих подтверждены **нумерация** (то же тождество «номер ↔
   `getportindex`», что измерено для 100/102) и **достижимость соседа** через
   `traceallports`; индекс порта соседа осмыслен.

   **Чего это не доказывает — и это главное.** Прогон был на портах этих типов,
   но **не через сам протокол**: `read_topology` их по-прежнему не читает,
   потому что фильтр не тронут. Решение о включении требует прогона пробы с
   расширенным фильтром и сверки полученного графа — следующий шаг, и он же
   первая ветка с собственной доказательной трассой на конкретный тип.

   **Замечание о `traceallports`, всплывшее здесь.** У `ToMem_0` в соседях
   оказался и `TimeGraphic_0`, хотя провод между ними не проводился: оба входа
   висят на одном выходе «Ступеньки».

   **Точная формулировка:** `traceallports` **не следует трактовать как
   перечисление непосредственных проводных соседей** — он может возвращать и
   другие порты той же связной компоненты. Чем это оказывается для протокола
   `conn`, разобрано в пункте 7: контрольное плечо показало, что лишняя связь
   возникает на блоках **текущего** фильтра, то есть это свойство протокола, а
   не следствие типов 104/106.

6. **Неполный диагностический контракт `_start_and_wait` — найден живым
   прогоном 2026-09-23, исправлен в `simintech-code` PR #19.** Пока модельное
   время не растёт, отказ утверждал, что «скрипт страницы не скомпилировался»,
   и отправлял проверять синтаксис пробы. Контрпример получен тут же: проба
   топологии на модели из **несоединённых** блоков дала ровно этот отказ при
   синтаксически **верном** скрипте — блок с неподключённым входом молча
   останавливает расчёт всей модели, и время стоит так же.

   Значит `time did not grow` не является доказательством
   `script did not compile`. Это дефект диагностического сенсора, а не
   формулировки: агент по такому тексту уходил чинить то, что не сломано, и не
   доходил до настоящей причины — структуры модели.

   Текст отказа теперь называет **состояние** и обе известные версии, не
   выбирая между ними. **Что осталось:** независимый признак причины —
   состояние компиляции, флаг ошибки, переход состояния расчёта. Искать его
   надо как независимый источник, а не как очередную интерпретацию того же
   симптома: первое прочтение `GetProjectStateFlag` уже показало, чем это
   кончается.

7. **`conn` описывает концы линии попарно, а не отдельные провода — и это
   свойство текущего протокола, а не следствие новых типов.** Найдено при
   подготовке расширения охвата; контрольное плечо показало, что к 104/106 это
   отношения не имеет — поведение воспроизводится на блоках текущего фильтра, с
   неизменённой библиотекой.

   Два прогона `read_topology` на моделях, отличающихся **только формой
   разветвления**:

   | модель | проводов физически | связей в `conn` |
   |---|---|---|
   | Один выход «Ступеньки» питает «Усилитель» и «Интегратор» | 2 | **3** |
   | Две независимые пары «Ступенька → Усилитель», «Ступенька → Интегратор» | 2 | 2 |

   В первом прогоне связей три, а проводов «по построению» два. Механизм:
   `traceallports` от порта возвращает не непосредственного соседа, а **всю
   связную компоненту**, и протокол пишет все пары её портов — для компоненты из
   `n` концов это `C(n,2)` рёбер. **Почему это не фантом, разобрано ниже**:
   разветвление с одного выхода среда хранит как одну линию с тремя концами.

   **Что показал трёхконцевой контроль с идентификаторами линий (тот же день,
   дальше).** Снята таблица «порт → `getportwireid` → `getportwires`» на том же
   разветвлении:

   | объект | порт | `getportwireid` | `getportwires` |
   |---|---|---|---|
   | `Step_source_1` | 0 | W = …633664 | `[W]` |
   | `kx_0` | 1 | **W′ = …634368** | `[W]` |
   | `Integrator_0` | 0 | W = …633664 | `[W]` |

   **Все три порта принадлежат одной линии W.** То есть SimInTech моделирует
   разветвление с одного выхода не двумя проводами, а **одной линией с тремя
   концами** (у линии в API есть и ветвление — `Wire.branch_to`).

   **Отсюда исправление предыдущего вывода.** Рёбра `B–C` — **не фантом**: эти
   порты действительно концы одной линии, и `conn` описывает её концы попарно.
   Точная формулировка: текущий генератор строит **попарное отношение портов
   внутри линии** (для линии с `k` концами — `C(k,2)` рёбер), а не множество
   непосредственных физических соединений. Это **потеря**, а не ложь: отличить
   одну разветвлённую линию от треугольника из трёх отдельных проводов по
   `conn` нельзя — но оба описания говорят правду о связности.

   **Открытая аномалия, найденная там же.** У `kx_0.1` `getportwireid` вернул
   `W′`, а `getportwires` — `[W]`: **две функции расходятся на одном и том же
   порту**. Объяснения нет; это отдельный вопрос к источнику, и он же —
   кандидат в оракул непосредственного ребра, если расхождение объяснится.

   **Дифференциальный тест структуры линии (2026-09-23).** Три топологии,
   отличающиеся только структурой проводки; для каждого порта сняты
   `getportwireid`, `getportwires`, `traceallports`:

   ```
   T1: одна линия (2 конца)      Step.0 → A   wires=[A]        trace: kx.1
                                 kx.1   → A   wires=[A]        trace: Step.0

   T2: ветвление двумя connect   Step.0 → A   wires=[A]        trace: Integr.0
                                 kx.1   → B′  wires=[A]        trace: Step.0, Integr.0
                                 Integr.0 → A wires=[A]        trace: Step.0

   T3: ветвление branch_to       Step.0 → A   wires=[A,B,C]    trace: kx.1, Integr.0
                                 kx.1   → A   wires=[A,B,C]    trace: Step.0, Integr.0
                                 Integr.0 → B wires=[A,B,C]    trace: Step.0, kx.1
   ```

   Что из этого следует:

   * **`getportwires` — не оракул ребра.** Он возвращает один и тот же набор для
     **всех** портов сети: в T3 все три порта видят все три линии. Он описывает
     связную сеть, как и `traceallports`, а не отдельный провод.

     Оба отказа — **результат дифференциального эксперимента над T1/T2/T3, а не
     два неудачных вызова.** Это граница доказанного знания: она не
     пересматривается при появлении следующего кандидата, потому что получена
     сравнением трёх заведомо различных структур, а не одним наблюдением.
   * **`getportwireid` — тоже не оракул.** Значение меняется от порта к порту
     внутри одной сети (в T2 «Усилитель» даёт `B′`, остальные `A`), и смысл его
     пока не установлен. Приписывать ему «непосредственный провод» оснований нет.
   * **Разветвлённая линия хранится как несколько объектов-линий.** Явный
     `branch_to` дал **три** идентификатора (`A`, `B`, `C`) там, где два `connect`
     дали один (`A`). То есть способ создания ветвления меняет внутреннее
     представление — и это ровно та структура, которую `conn` теряет.
   * **`traceallports` не симметричен.** В T2 от `Step.0` достижим только
     `Integrator.0`, а от `kx.1` — оба. Направление обхода влияет на результат.
     Это самостоятельное наблюдение, и оно ставит под вопрос текущий `conn` — но
     уже с другой стороны, чем раньше.

   **Оракул непосредственного ребра найден: `findstartport` (замер 2026-09-23).**
   Та же тройка топологий, для каждого порта — `mode`, `findstartport`,
   `findendport`:

   | | порт (mode) | `findstartport` | `findendport` |
   |---|---|---|---|
   | T1 | `Step.0` (out) | — | `kx_0.1` |
   | | `kx_0.1` (in) | `Step_source_1.0` | — |
   | T2 | `Step.0` (out) | — | `Integrator_0.0` |
   | | `kx_0.1` (in) | `Step_source_1.0` | — |
   | | `Integrator_0.0` (in) | `Step_source_1.0` | — |
   | T3 | `Step.0` (out) | — | **`kx_0.1`** |
   | | `kx_0.1` (in) | `Step_source_1.0` | — |
   | | `Integrator_0.0` (in) | `Step_source_1.0` | — |

   **`findstartport` на каждом входном порту возвращает ровно тот выход, который
   его питает** — во всех трёх конфигурациях, включая ветвление. Это и есть
   искомое отношение «непосредственное ребро», причём в форме, которая не
   зависит от асимметрии `traceallports`.

   **Отсюда конкретный путь исправления.** Вход у линии ровно один (в отличие от
   выхода, который может ветвиться), поэтому достаточно **обойти входные порты**
   и у каждого спросить `findstartport`: для линии с `k` концами получится ровно
   `k−1` рёбер — сколько их и есть, без клики и без опоры на `traceallports`.

   **`findendport` на эту роль не годится:** у ветвящегося выхода он возвращает
   только **один** вход из нескольких. При этом T2 и T3 он различает — в T2 это
   `Integrator_0.0`, в T3 `kx_0.1`, — что согласуется с различием их внутреннего
   представления (`branch_to` дал три линии, два `connect` — одну) и с прежним
   расхождением `getportwireid`.

   **Подтверждение на реальной модели (2026-09-23).** Тот же скан на копии демо
   вендора, **все** порты страницы, 128 штук:

   | mode | портов | `findstartport` ≠ 0 | `findendport` ≠ 0 |
   |---|---|---|---|
   | 0 (вход) | 64 | **64** | 0 |
   | 1 (выход) | 64 | 0 | **64** |

   Разделение идеальное: у входов работает только `findstartport`, у выходов
   только `findendport`, и **каждый вход разрешается в источник**. Это первое
   подтверждение оракула на модели, построенной не нами.

   **Разложение всех 31 потери — измерено (2026-09-23).** Проба с preflight
   (страница доказана как та самая и исполнимая) дала обе части:

   | потеря | причина | как измерена |
   |---|---|---|
   | 28 | источник относится к типу **111** (объекты `Bridge`) и отброшен фильтром | у 28 из 32 входов `findstartport` вернул тип 111 |

   `28 + 3 + 1 = 32` — эталон сходится, `extra = 0`. То есть генератор ничего не
   выдумывает: он теряет по двум независимым причинам, и обе названы.

   **НО вывод «три потери объясняются ограничением владельца» оказался неверным
   (проверено в тот же день, offline + живой замер).** Владельцы действительно
   различаются — и это измерено числами:

   ```
   Macro235.0   ← k1.0   same-owner   2455561571904 / 2455561571904
   acrms_Q_P3.0 ← k6.0   DIFF-owner   2455561571904 / 2454814970240
   acrms_Q_P4.0 ← k6.0   DIFF-owner   2455561571904 / 2454814966912
   acrms_Q_P5.0 ← k6.0   DIFF-owner   2455561571904 / 2454814956928
   ```

   Но **эталон вообще не содержит связи `k6 — acrms_Q_P3`**. Его связи с этими
   портами — другие:

   ```
   (Key_manual_button_1, 0) ↔ (acrms_Q_P3, 0)
   (Key_manual_button_2, 0) ↔ (acrms_Q_P4, 0)
   (Key_manual_button_3, 0) ↔ (acrms_Q_P5, 0)
   ```

   То есть `findstartport(acrms_Q_P3.0)` вернул `k6.0`, а эталон считает, что
   этот вход питает `Key_manual_button_1.0`. **`findstartport` и вендорский
   эталон расходятся по конкретному ребру.** Ограничение `srcowner == objowner`
   не объясняет эту потерю — оно лишь прячет расхождение, потому что `k6` лежит
   вне контейнера.

   Отсюда правильный статус: `findstartport` доказан как оракул **на построенных
   моделях и в агрегате по демо**, но на этих трёх портах он даёт ответ,
   противоречащий эталону. Это первый контрпример к нему, и он требует разбора
   прежде, чем менять генератор ещё раз. Гипотезы, требующие измерения: либо
   нумерация портов у этих объектов расходится с `getportindex`, либо
   `findstartport` проходит сквозь служебный слой и возвращает не тот конец.

   **Маршрут измерен — и обе гипотезы получили ответ (2026-09-23).** Повторное
   применение `findstartport` от трёх входов, по 12 шагов на каждый:

   ```
   acrms_Q_P3.0 → k6.0   (тип 100, индекс 0, mode 1 — ВЫХОД)   … и остановка
   acrms_Q_P4.0 → k6.0   (то же)
   acrms_Q_P5.0 → k6.0   (то же)
   ```

   **Гипотеза адресации снята.** Независимое опознание портов совпало:
   `getblockportid(acrms_Q_PX, 0)` даёт индекс 0 и `mode 0`;
   `getblockportid(Key_manual_button_1, 0)` — индекс 0 и `mode 1`. Нумерация
   однозначна, расхождения номеров нет.

   **Осталась и усилилась вторая гипотеза, но в другой форме.** И `k6.0`, и
   `Key_manual_button_1.0` — **выходы**, и оба оказываются выше одного и того же
   входа `acrms_Q_P3.0`. Один вход не может иметь двух драйверов, если связь
   парная; но линия в SimInTech, как уже измерено, **может иметь несколько
   концов**. Тогда верная формулировка семантики такая:

   > `findstartport(вход)` возвращает **один из upstream-концов линии**, а не
   > терминальный источник и не обязательно тот конец, который записан
   > вендорским эталоном.

   На T1/T2/T3 и в агрегате по демо это совпадало с нужным концом, потому что
   там линии были простыми; на этих трёх — не совпало.

   **Второй измеренный факт, важный для traversal:** на **выходном** порту
   `findstartport` возвращает `0`. Справка это и утверждает («по заданному
   идентификатору конечного **входного** порта»), и замер совпал: маршрут
   останавливается там, где доходит до выхода. Значит **цепочку нельзя пройти
   повторным применением одной и той же функции** — за выходом она не
   продолжается.

   **Gate B — маршрут через мосты, первая часть.** Все 28 входов с источником
   111 сходятся всего на **два моста**: `Bridge9` и `Bridge10`
   (`Macro263.0 → Bridge9`, `Macro263.1 → Bridge10`, и так далее). Структура
   моста измерена:

   | порт | `mode` | `findstartport` | `findendport` |
   |---|---|---|---|
   | `Bridge9.0` | **2** | 0 | `Bridge7.0` |
   | `Bridge9.1` | 0 | `Bridge7.0` | — |
   | `Bridge9.2` | 0 | `Bridge11.0` | — |
   | `Bridge10.0` | **2** | 0 | `Bridge6.0` |
   | `Bridge10.1` | 0 | `Bridge8.0` | — |
   | `Bridge10.2` | 0 | `Bridge12.0` | — |

   У моста один ненаправленный порт и два входных; цепочка уходит на другие
   мосты (`Bridge7`, `Bridge11`, `Bridge8`, `Bridge12`). **Однозначность
   маршрута пока не установлена**: какой из портов моста принимает вход и какой
   ведёт дальше — не измерено, а без этого «пройти насквозь» лишь гипотеза.
   Это следующая ступень Gate B, и менять генератор до неё нельзя.

   **Языковая находка, стоившая трёх прогонов.** `var a, b, c: integer` —
   группировка объявлений — в этом диалекте **недопустима**: у каждой переменной
   должен быть свой тип. Нарушение не даёт сообщения: скрипт молча не
   компилируется, расчёт не идёт, и мост сообщает «модельное время не растёт».
   Именно на этом упали три прогона подряд, пока preflight не отделил причину.

   **Заодно измерен `mode = 2` — тот самый не встретившийся ранее edge case.**
   У мостов такие порты есть, и поведение функций на них различается:

   | порт | `mode` | `findstartport` | `findendport` |
   |---|---|---|---|
   | `Bridge9.0` | 2 | **0** | `Bridge7.0` |
   | `Bridge9.1` | 0 | `Bridge7.0` | — |
   | `Bridge9.2` | 0 | `Bridge11.0` | — |

   То есть **на ненаправленном порту `findstartport` возвращает 0**, а
   `findendport` — конец. Это не отменяет генератор (он ходит от `mode = 0`, где
   оракул подтверждён), но закрывает вопрос «а что на `mode = 2`»: там его звать
   нельзя, и теперь это измерено, а не предположено.

   **Что ещё видно про мосты.** Они образуют цепочки (`Bridge7 → Bridge9 →
   Bridge11`), то есть служебный слой — не один прозрачный узел, а сеть. И у
   моста есть порты с `mode = 2` наряду с `mode = 0`. Traversal через них
   остаётся неизмеренным: чтобы его доказать, нужен переход по обоим концам, а
   не одна ступень.

   **Методический результат прогона.** Первые две попытки упали на «модельное
   время не растёт», и **preflight отделил причину**: минимальное тело
   (`preflight 68 128`) исполнилось, а тело пробы — нет, значит отказ был в теле,
   а не в странице. Причина в теле оказалась синтаксической: `if/else` с
   многострочными вызовами внутри молча не компилируется, и расчёт не идёт.
   Переписывание на переменную-метку (`ownk`) сняло отказ. Это ровно то
   разделение PRECHECK/PROBE, о котором шла речь, и оно окупилось с первого раза.

   **Ещё раз подтверждён дефект #19.** Ветка растёт от `main`, где исправления
   нет, и сообщение снова сказало «скрипт не скомпилировался» — при том что
   синтаксис в первом случае действительно был сломан, а модель при этом не
   считалась по той же причине. Различить «скрипт не собрался» и «модель не
   пошла» по этому тексту по-прежнему нельзя.

   | mode | портов | `findstartport` ≠ 0 | `findendport` ≠ 0 |
   |---|---|---|---|
   | 0 (вход) | 64 | **64** | 0 |
   | 1 (выход) | 64 | 0 | **64** |

   Разделение идеальное: у входов работает только `findstartport`, у выходов
   только `findendport`, и **каждый вход разрешается в источник**. Это первое
   подтверждение оракула на модели, построенной не нами.

   **Оба edge case при этом не встретились в этой выборке — и это надо знать до
   правки.** Ненаправленных портов (`mode = 2`) **среди портов 100/102** нет
   вовсе (позже они нашлись у объектов типа 111 — см. ниже); входов без
   источника тоже не нашлось. Поэтому:

   * поведение `findstartport` на **неподключённом входе** остаётся
     неизмеренным. Косвенный довод за осторожность: по эталону у страницы 32
     входа **с проводом** из 64, а скан вернул источник для всех 64 — значит либо
     неподключённых входов на этой странице нет, либо `findstartport` отвечает
     чем-то и для них. Различить по этому прогону нельзя, и гадать не нужно:
     генератор обязан **проверять результат на 0 явно** и не создавать `conn`,
     если источника нет;
   * `mode = 2` — тем более: раз такого порта не нашлось, ветка для него в
     генераторе пишется защитно, а не по измерению.

   **Отдельно измеренное препятствие для конструкции «конец вне фильтра».**
   Связь `104 → 100` через библиотеку **не создаётся**: `PortError`. Значит
   сценарий «вход включённого типа питается выходом исключённого» этой дорогой
   не построить. Политику для него надо брать из уже принятой в extractor:
   **фильтр применяется к обоим концам**, и `conn` не должен ссылаться на порт,
   которого нет в фазе `port`, — иначе разбор отвергнет снимок целиком (это
   закреплено `parse_topology`).

   **Связь `wireid` с `findstartport` — измерена, противоречия нет
   (2026-09-23).** Тот же скан, добавлен `getportwireid`:

   | mode | провод | `findstartport` | `findendport` | портов |
   |---|---|---|---|---|
   | 0 | ≠ 0 | ≠ 0 | 0 | 64 |
   | 1 | ≠ 0 | 0 | ≠ 0 | 64 |

   **Портов без провода на странице нет вовсе**, поэтому контрпримера к
   «`wireid ≠ 0` ⇔ есть источник» здесь не нашлось — но и случай
   «неподключённый вход» эта страница дать не может.

   **Кажущееся противоречие «64 против 32» объясняется разложением портов.** Их
   128, и это две разные половины: **64 — порты модельных блоков** (типы
   100/102), **64 — порты объектов-линий** (тип 101; таких объектов 32, по два
   порта). Эталонное «64 записи о портах с проводом (32 входа и 32 выхода)» —
   одна из этих половин, а не половина от 128. Так что `findstartport` на всех
   64 блочных входах даёт источник, и это **не** значит, что он отвечает и на
   неподключённых: неподключённых здесь просто нет.

   **Побочно установлено: объект-линия (101) сам имеет порты** (`mode` 0 и 1) и
   участвует в отношении концов — `MBTYWire.0` (выход) имеет `findendport` =
   `kx.1`, а `MBTYWire.1` (вход) — `findstartport` = `k1.0`. То есть `101` —
   не «провод» в смысле ребра, а объект с собственными концами, и это ещё один
   довод не считать его ребром.

   **Протокол нового формата пока не проектируется осознанно.** Сначала
   объяснение аномалии `W′` и проверка `findstartport`/`findendport`: возможно,
   у источника уже есть готовое представление «линия → её концы», и тогда новый
   формат будет его пересказом, а не изобретением.

   **Что остаётся верным для решения о 104/106.** Включение типов ничего не
   ломает и ничего не чинит. «Protocol-compatibility gate» для них честно не
   закрывается не потому, что типы плохи, а потому что **сам протокол теряет
   форму линии** — и это надо решать независимо от охвата.

   **Статус 104/106 заморожен (2026-09-23).** У обоих подтверждены существование
   в COM, тождество нумерации портов и достижимость соседа; решение о включении
   — **BLOCKED**, и причина названа точно: недостаточная выразительность
   текущего протокола, а не свойства этих типов. Заморозка важна процедурно:
   иначе легко вернуться к расширению охвата, хотя вопрос теперь относится к
   семантической потере на уровне всего `topology extractor`.

   **Измерено живьём 2026-09-23.** Четыре схемы, два генератора; «строки» —
   записи `conn`, «пары» — после канонизации:

   | схема | `main` (все соседи) | вендорское правило (`min(1)` для входов) |
   |---|---|---|
   | демо вендора | 64 строки → **32 пары = эталон** | 64 строки → **32 пары = эталон** |
   | T1 (одна линия) | 2 → 1 | 2 → 1 |
   | T2 (два `connect`) | 4 → 3 | 3 → 2 |
   | T3 (`branch_to`) | 6 → **3 (треугольник)** | 4 → **2 (звезда)** |

   Фаза 3 из `main` запускалась телом пробы **дословно** (`git show
   main:simintech_api/topology.py`, сняты только фазы 1–2, на строки `conn` не
   влияющие); вендорское правило — отдельным телом, отличающимся ровно строкой
   `min(1, …)`. Обе пробы на демо сверены с эталоном по ключам: **совпадение
   полное, лишних 0, пропавших 0**.

   Два вывода, каждый со своей областью:

   * **Демо оракулы не различает.** Там это и не могло быть иначе: у всех 32
     линий ровно два конца (измерено: портов 64, линий 32, размеры линий
     `{2: 32}`), поэтому все способы дают одно и то же. Как контроль
     различающей силы демо бесполезно — различает только T3.
   * **На развилке `main` расходится с вендором.** Вендор описывает развилку
     **звездой** (лучи — от выхода), `main` — **треугольником** (`C(k,2)` пар).
     «Фантомное ребро» `B–C` из пункта 7 — ровно то ребро, которого вендорский
     экспортёр не пишет. Значит оно не свойство протокола, а **расхождение
     нашего генератора с контрактом поставки**.

   **Почему `min(1)` корректен — измерено на 64 портах демо.** `traceallports`
   отдаёт не соседа, а **всю компоненту**: на T1 у входа один сосед, на T3 —
   два, включая брата по разветвлению. При этом первый элемент компоненты у
   **всех 32 входов демо** — порт режима `1` (выход), а у всех 32 выходов — порт
   режима `0`. То есть обрезка до первого элемента выбирает направленный
   «источник» не случайно. Оговорка честная: это измеренная регулярность
   (64 порта демо + T1/T3), а не доказанное свойство порядка; контрпример не
   искался.

   **Чем закрывается `findstartport` — и вместе с ним `missing 31`.** Сырые
   соседи `traceallports` по всем 64 портам демо сняты телом пробы: у
   `acrms_Q_P3.0` сосед ровно один — `Key_manual_button_1.0`, ровно то, что
   записано эталоном. Объект `k6`, который вернул `findstartport`, **не
   встречается в контейнере ни разу**: ни в одном списке соседей, и его нет
   среди 35 объектов эталона (похожий по имени `k1` — есть, и он действительно
   в контейнере). Значит `findstartport` вернул порт **другого контейнера**: это
   сигнальный резолвер, а не оракул электрической смежности, и его результат
   законно отбрасывается фильтром владельца. Отсюда: `missing 31` —
   **регрессия, внесённая подменой оракула**, а не свойство среды. Ветка
   `fix/topology-conn-from-findstartport` остаётся незелёным exploratory
   результатом, PR по ней не открывается.

   **Что даёт wire-API — то, ради чего он проверялся.**

   * `tracestartportwires(port)` в поставке 2.26.6.23 **работает**: имя из
     реестра подтверждено живым вызовом, а не наличием в
     `language_functions.json`. Возвращает упорядоченный список **сегментов**
     пути от порта к корневой линии — на T3 у `Integrator_0.0` это `[W2, W1]`,

     ветвящегося сегмента**; этим же объясняются нули предыдущего прогона.

   * `getwirestartpointcoord` / `getwireendpointcoord` возвращают тип `point`,
     которого нет в списке разрешённых типов пробы: их включение — отдельное

   **Аномалия `W′` из пункта 7 объясняется фикстурой, а не средой.**

   «лишние рёбра к объекту линии», а «фантомные» оставлены только там, где речь
   о **разветвлении**, с явной оговоркой, что это другой случай.

   **Отдельная заметка про прибор, а не про среду.** Первый замер этого вклада
   дал ноль строк, и это было прочитано как «тело не скомпилировалось» — с
   гипотезой про вложенные вызовы в `writelnutf8` и унарный минус. Ни то, ни
   другое не подтвердилось: причиной была ошибка в **считывателе** замера
   (`result.lines` — список строк, а индексировался как список полей, `r[0]`
   сравнивался с `"object"`). Тело работало всё время, включая то, что было
   написано с нуля. Урок: отказ прибора и отказ среды различаются **контрольным
   прогоном заведомо рабочего тела в том же батче** — он и был добавлен, и он же
   снял ложный вывод.

9. **Трек wire-shape recovery (2026-09-23): форму линии wire-API отдаёт частично.**
   Вопрос ставился так: можно ли независимо восстановить структуру ветвления из
   уже найденных wire-примитивов. Ответ измерен на пяти своих фикстурах и на демо
   вендора; production-код не менялся.

   **Что восстанавливается.** Дерево сегментов: корень — линия с
   `getparentwireid = 0`, дети — по `getparentwireid`, порты привязываются картой
   «порт → `getportwireid`», источник — порт режима 1. На прямой линии, одной
   ветви и двух ветвях реконструкция совпала с замыслом фикстуры (корень
   `Step_source_1.0 ↔ kx_0.1`, ветви — к входам потребителей).

   **Чего API не отдаёт — измерено.**

   * **Объект точки ветвления невидим.** COM видит линий больше, чем атрибутирует
     wire-API: прямая — 1 и 1, одна ветвь — 3 и 2, две ветви — 4 и 3 (и с
     явными `point_index` 0/1 тоже 4 и 3). Разница равна числу точек ветвления;
     сама точка не имеет порта и ни в один путь не входит. Значит **истинное число
     сегментов из wire-API не выводится** — нужен COM-оракул (`Page.get_wires()`).
   * **Индекс узла не различает ветви.** И с `point_index` по умолчанию, и с явно
     заданными 0 и 1 обе ветви сообщают одно и то же: родитель — корень, узел 1.
     Двух точек ветвления на одной линии получить не удалось, и
     `getparentwirenodeindex` различающим ключом **на измеренных случаях** не
     является.
   * **Вложенное ветвление не строится.** `branch_to` от ветви новой линии не
     создаёт (COM: 3 линии — столько же, сколько у одной ветви), а вход целевого
     блока остаётся неподключённым, и модель перестаёт считать. Проба при этом
     **успевает исполниться и записать полный результат** — в файле оба маркера, —
     и только после этого мост отказывает «время не растёт». Это уточняет контракт
     отказа из пункта 6 и PR #19: исполненность скрипта и рост времени — разные
     признаки, и здесь они разошлись.
   * **Путь уходит за границу контейнера, и родительские связи этого не
     описывают.** На демо у 31 порта из 64 путь состоит из двух сегментов, и
     второй — **отдельный корень** (`parent = 0`), не связанный с первым
     родительскими связями: портов в контейнере у него нет (0 из 31), на главной
     странице его нет (0 из 31), и ни один второй сегмент не бывает чьей-то
     родительской линией. То есть `tracestartportwires` продолжение **видит**, а
     `getparentwireid` его **не описывает** — примитивы расходятся.
   * **Где продолжение.** **3 из 31** — в субстранице блока-соседа
     (`Key_manual_button_1/2/3`); это ровно те входы, из-за которых `findstartport`
     вернул `k6`, то есть две независимые меры сошлись. Остальные **28** не
     нашлись ни в субстранице соседа, ни двумя уровнями глубже, ни на главной
     странице, причём субстраницы соседей читались — это «искал и не нашёл», а не
     «не смог заглянуть». Совпадение числа 28 с прежним разложением потерь (28 из
     31 — первый переход на объект типа 111, мост) — **соответствие, а не вывод**;
     проверка требует заглянуть в объекты-мосты и в этом треке не делалась.
   * Идентификаторы линий — **адреса экземпляра проекта**: одна и та же фикстура
     в разных прогонах дала разные id. Реконструкция возможна только внутри одного
     прогона, сохранять эти id нельзя.

   **Вывод трека.** Wire-API достаточен для **дерева сегментов внутри
   контейнера** — корень, ветви, привязка портов — и недостаточен для полной формы
   линии: точка ветвления невидима, число сегментов без COM-оракула не выводится,
   индекс узла ветви не различает, вложенность не строится, а продолжение за
   границей контейнера видно, но родительскими связями не описывается.
   `connections` остаётся тем, чем объявлен, — отношением связей; полное
   представление проводки потребует разбираться и с невидимой точкой ветвления, и
   с расхождением пути и родителя.

   **Подтрек: локализация 28 продолжений через объекты типа 111 — проверен,
   ответ отрицательный (2026-09-23).** Цель формулировалась узко: выяснить
   происхождение оставшихся продолжений и проверить, локализуются ли они через
   bridge objects. Совпадение «28 ↔ тип 111» оставалось корреляцией и здесь
   проверялось, а не предполагалось.

   * **В контейнере нет объектов типа 111 вовсе** — измерено переписью по всем
     68 объектам: типы `100×2, 101×32, 102×33, 108×1`. Значит из этого контейнера
     корреляция «28 ↔ 111» не подтверждается: упираться не во что, объектов этого
     типа здесь нет.
   * **Рекурсивный обход всей иерархии проекта нашёл 3 продолжения из 31** — те
     же три, в субстраницах кнопок (`acrms_Circuit1/Key_manual_button_1/2/3`).
     Остальные **28 не найдены нигде**: пройдено 68 страниц, глубина до 6, бюджет
     обхода израсходован не полностью (осталось 332 из 400), то есть обход
     **завершился**, а не оборвался.
   * Отсюда: 28 продолжений **не являются линиями, лежащими на какой-либо
     достижимой странице проекта**. Они видны `tracestartportwires`, но
     COM-перечислением не находятся — либо принадлежат слою, не выставляемому
     страницами, либо не обозначают страничный объект вовсе.

   **Что это меняет для трека.** Граница стала резче: продолжение пути может
   указывать на сегмент, которому **не соответствует ни один объект-линия**,
   достижимый обходом страниц. Значит `tracestartportwires` нельзя читать как
   способ перечислить объекты линии: он отдаёт идентификаторы, часть которых не
   подтверждается ничем другим. Прежнее разложение «28 из 31 — первый переход на
   объект типа 111» остаётся корреляцией **того** замера (там источником был
   `findstartport`, а он ходит за пределы контейнера); здесь оно не подтвердилось
   и не опровергнуто — проверялась локализация через объекты контейнера.

10. **104/106: все проверяемые инварианты проходят — ограничивает граница охвата
    контракта.** Диагностика 2026-09-23, вопрос ставился узко: найти недостающий
    инвариант протокола, из-за которого типы заморожены. Измерено на своём проекте
    («Ступенька» → «В память» (104) и → «Временной график» (106), оба входа
    подключены — иначе модель не считает, см. пункт 6):

    * **адресация проходит**: `getportindex(getblockportid(obj, 0)) = 0` у обоих —
      то самое тождество, ради которого фильтр типов и держится;
    * **ownership проходит**: владелец у всех трёх объектов один, у всех соседей
      признак «тот же владелец» равен 1;
    * **перечисление портов проходит**: порт виден (`Y3` у 104, `inport_1` у 106);
    * **страж наличия линии проходит**: `getportwireid ≠ 0` у обоих;
    * **выходных портов нет ни у одного** — `PortError` на `get_out_port(0)`.

    Значит **ни один из четырёх названных кандидатов не является блокирующим**.
    Ограничение другое и структурное: 104 и 106 в контейнере связаны между собой,
    а фаза объектов объявляет только 100/102, поэтому строка `conn` сослалась бы на
    необъявленный объект и разбор отверг бы модель **целиком**. Включение требует
    согласованного проведения типов в **трёх** местах — отбор объектов, отбор
    портов, страж типа соседа; иначе связь к ним тихо теряется.

    **Решающее — граница охвата.** Вендорский экспортёр объявляет только 100/102
    (`export_sheme_functions.inc:44-50`), и эталон снят именно его скриптом.
    Поэтому включение 104/106 — **сознательное расширение за пределы контракта
    поставки**: паритет с эталоном, закреплённый PR #20, на моделях с 104/106
    разойдётся по определению (на демо их нет: типы контейнера — 100×2, 101×32,
    102×33, 108×1).

    **Измеренный eligible set (перепись по кандидатам, 2026-09-23).** Телом,
    снимающим четыре условия сразу, обойдены все классы, которые удалось создать:
    `100` («Усилитель» 2 порта, «Сумматор» 3 порта, «Ступенька» 1), `104` («В
    память», 1 вход), `106` («Временной график», 1 вход) — **адресация держится у
    всех**: `getportindex(getblockportid(obj, i)) = i`, включая трёхпортовый
    «Сумматор»; порты перечислимы, `getportwireid` и `getportinfo` применимы.
    Классы «Из памяти» (105), «Блок со встроенным интерпретатором» (109) и
    «Блок-узел» (113) **создать не удалось** (`UnsupportedBlockError`, `BlockError`),
    поэтому в набор они не входят **не потому, что провалили критерий**, а потому
    что измерить их не на чем; основания разные, и это названо.

    **Отрицательный случай измерен, а не объявлен.** Тот же критерий, применённый к
    **линии** (тип 101), даёт отказ по существу: у третьего провода
    `getportindex(getblockportid(wire, 1))` вернул **2**, а не 1, — тождество
    адресации на линии не держится (то же расхождение измерено в пункте 4). То есть
    критерий отсекает линию **данными**, а не тем, что её тип не перечислен в
    списке. Подпись (тип 108) имеет 0 портов, и её отсекает условие «не
    презентационная инфраструктура».

    **Граница критерия, найденная тут же.** «Не презентационная инфраструктура»
    проверяется типом, а **комментарий имеет тип 100** (`RTFComment_0`, 0 портов):
    от комментария критерий модельный объект не отличает. Это не дефект критерия, а
    его граница — комментарий объявляется и сегодня, и пробой, и вендором.
    Записано, чтобы это не выглядело случайностью.

    **Побочно измерено про 104/106:** `set_in_port_count` на них **добавляет** вход
    (у «В память» и «Временного графика» 1 → 2), тогда как на «Сумматоре» (тип 100)
    он задаёт число точно (2 → 1 → 3). Кто станет сводить число входов у 104/106
    этим методом, получит лишний неподключённый вход и — по механизму из пункта 6 —
    неподвижное модельное время.

    **Реализовано 2026-09-23, PR `simintech-code#21`.** Критерий — одна константа
    `ELIGIBLE_OBJECT_TYPES` (100, 102, 104, 106) и построитель `_type_guard`, из
    которого собираются **все четыре** места фильтра (три фазы плюс тип соседа):
    литеральных копий набора в теле не осталось, новый тип добавляется правкой
    одного места. Мутации проверены: расширение критерия краснит 1 тест, тело,
    отставшее от критерия, — 2.

    Строгий разбор не тронут **ни строкой** (проверено диффом), поэтому висячая
    ссылка невозможна по построению, а паритет на демо сохранился: сверка с
    эталоном зелёная, потому что 104/106 на демо не встречаются. Живые тесты
    доказывают новое: объекты объявлены, порты адресуются, связи к ним больше не
    теряются, а отказ адресации у линии воспроизводится измеримо.

    **Что признано переставшим быть верным.** Прежний пример «страница с
    единственным блоком „В память“ читается как 0 объектов» **неверен с этой
    правки** — тип проходит критерий. Замена примеру отдельным замером не
    подтверждена, и в документах это сказано прямо, а не переписано по догадке.
    Также измерено попутно: `Block.get_name()` у 104/106 возвращает пустую строку,
    поэтому сопоставлять их надо по классу, а имя в протокол даёт языковая
    `getobjname`.

    **Тот же класс ошибки повторился на ревью #21 — и снова его нашла сверка, а не
    чтение.** В двух живых документах (`build_topology_probe` и `CLAUDE.md`)
    остался тезис «отбор исключает 104/106», прямо противоположный новому
    контракту; в `CLAUDE.md` это особенно нежелательно, потому что по нему
    следующий читатель получил бы старую модель охвата. Сквозной поиск **по
    формулировкам**, а не по изменённым строкам, нашёл и третье место — в
    датированном плане 2026-09-21; план не переписан (это запись решения), но
    помечен датированной пометкой. Ни тесты, ни CI этого поймать не могли: правка
    документационная и тела пробы не касается (проверено сверкой тела до и после).
    Урок тот же, что при переносе `#20`: **свой результат проверяют сверкой по
    источнику, а не просмотром сделанного**.

    **Охват вендора теперь ИЗМЕРЕН, а не прочитан.** Вендорская процедура
    `export_1layer_topology` запущена дословно (объявление процедуры в теле пробы
    работает — проверено отдельным опытом), и первым делом на демо: её вывод
    **побайтово равен нашему эталонному файлу** (39 977 байт, 35 объектов, 64
    записи `ConnectedTo`). Это и контроль запуска, и независимое подтверждение
    того, что эталонный файл есть ровно её вывод.

    На модели с 104/106 её вывод такой: объявлен **один** объект (`Step_source_1`,
    тип 100), а в его же `ConnectedTo` стоит ссылка на `TimeGraphic_0` (тип 106),
    **которого в списке объектов нет**. То есть вендор **не объявляет** 104/106, но
    **ссылается** на них, и его формат висячую ссылку терпит. Наш разбор —
    сознательно строгий и такую ссылку отвергает целиком; именно поэтому проба и
    теряет такие связи молча (пункт про цену фильтра). Отсюда развилка стала
    предметной: паритет означает «как вендор» (висячие ссылки, то есть ослабление
    строгости разбора), надмножество — «объявлять и их» (расхождение со
    множеством объектов вендора, нужен свой критерий сверки), а текущее поведение —
    третий вариант, «тихо терять связь».

    **Чего в этом замере по-прежнему нет.** Тождество адресации проверено на
    **одном порту** у каждого типа: много портов у 104/106 получить не удалось,
    поэтому класс расхождений, найденный в пункте 4 на объекте линии (разные
    индексы для одного и того же порта), здесь не воспроизводим.

    **Побочно (вне 104/106, но переиспользуемо).** Вендорский код запускается в
    теле пробы, но требует одного условия: процедура **сама присваивает `fid`**
    (`fid = createfile(afilename,-1)`), а `fid` — тот же дескриптор, которым пишет
    мост, поэтому её нужно обернуть в сохранение и восстановление. Проверено
    отсутствием: без этого в файле результата остаётся **только**
    `SCRIPT_BRIDGE_BEGIN` (маркер конца уходит в чужой дескриптор), а мост
    отказывает с **`PermissionError`** на своём же файле результата — то есть отказ
    маскируется под проблему доступа. С сохранением и восстановлением тот же
    вызов проходит и даёт файл, равный эталону.

    **Решено 2026-09-23: надмножество — с явным критерием топологической
    допустимости.** Вендорский экспорт не становится нормативным object-set: он
    оптимизирован под собственный формат и допускает висячую ссылку, тогда как наш
    API — семантическое представление модели. Поэтому критерий сверки заменяется:
    сравнивать надо не «что объявляет вендор», а **что допустимо для нашего
    протокола**, и критерий этот измеряемый:

    * COM однозначно адресует объект;
    * COM перечисляет его порты;
    * `getportindex(getblockportid(obj, i)) = i`;
    * `getportwireid` и `getportinfo` к нему применимы;
    * объект не является линией или презентационной инфраструктурой.

    Для текущей версии это даёт **измеренный** набор, расширенный 104/106, но **не
    превращается в правило «все типы кроме 101»**: новые типы добавляются только
    после замера их соответствия критерию. Вендорская выгрузка остаётся полезной
    как **compatibility oracle для пересечения наборов**, а не как определение
    полного охвата. Строгий разбор при этом сохраняется строгим: висячая ссылка у
    нас невозможна по построению — второй конец объявляется.

    Форма изменения — **новая версия topology-контракта**, а не правка трёх строк
    фильтра: меняется критерий охвата и его обоснование. Третий вариант — нынешнее
    молчаливое выпадение связи — назван тем, чем был: следствием политики разбора,
    а не отдельным решением контракта.

11. **Столкновение владения дескриптором `fid` — отдельный трек, не часть
    104/106.** Найдено попутно 2026-09-23 при запуске вендорской процедуры.
    Минимальное условие воспроизведения: **процедура внутри тела пробы
    присваивает `fid`** — вендорская делает это первой же строкой
    (`fid = createfile(afilename,-1)`) и в конце освобождает его. `fid` — тот же
    дескриптор, которым пишет мост, поэтому после вызова маркеры результата уходят
    в чужой дескриптор.

    Измерено **отсутствием** сохранения: в файле результата остаётся только
    `SCRIPT_BRIDGE_BEGIN`, а мост отказывает с `PermissionError` на своём же файле
    результата. Диагностика при этом **вводит в заблуждение** — отказ выглядит как
    проблема доступа к файлу, тогда как причина в нарушении владения дескриптором
    внутри одной пробы. С сохранением и восстановлением (`saved_fid`) тот же вызов
    проходит и даёт файл, побайтово равный эталону.

    Почему это отдельный трек: дефект **владельца ресурса**, а не политики охвата
    объектов. Вопрос «что должен делать мост, если тело переопределило `fid`» —
    про жизненный цикл пробы, и он становится важен ровно тогда, когда
    **вендорские процедуры предполагаются поддерживаемым механизмом расширения**.
    Если да — нужен либо контракт именования дескрипторов, либо явное
    сохранение/восстановление в мосте, либо честная диагностика («тело
    переопределило дескриптор результата») вместо `PermissionError`.

    **Решено 2026-09-23: берётся в production — вендорские процедуры считаются
    поддерживаемым механизмом расширения.** Тогда столкновение `fid` нельзя
    оставлять исследовательской заметкой. Архитектурно выбирается **изоляция, а не
    соглашение об имени**:

    ```text
    мост владеет дескриптором результата
        ↓
    вендорская процедура получает изолированный дескриптор/контекст
        ↓
    вендорский код пользуется своими переменными
        ↓
    дескриптор моста не может быть молча подменён
    ```

    Если COM и встроенный язык такого разделения не позволяют, допустимый
    production-контракт обязан **явно сообщать несовместимость** вместо
    маскирующего `PermissionError`: вызывающий должен прочитать «тело
    переопределило дескриптор результата», а не «отказано в доступе к файлу».

    **Что остаётся исследовательским и решений не блокирует:** причина выбора
    первого соседа `traceallports` (чисто объяснительный вопрос — совместимость от
    него не зависит), оставшиеся continuation-paths типа 111 и семантика
    `findstartport`. И **PR #20 ни от одного из этих решений не зависит**: он
    остаётся отдельной завершённой correction с доказанным вендорским контрактом и
    проходит свой review/merge независимо от новой политики охвата.

    **Итог 2026-09-24:** вопрос «даёт ли язык область видимости под дескриптор»
    измерен, правка сделана отдельным PR (`simintech-code` #22). Разбор — §10.11.

12. **Живой замер требует машины без запущенного SimInTech (2026-09-23).**
    Измерено на себе: при двух работающих `mmain.exe` (PID 3780 и 38232, старт
    14:37 и 15:08) клиент `COMClient.connect()` **своего процесса не поднял** — а
    `get_process_id()` вернул PID уже работающего. Раз PID 3780 был жив, новый
    процесс не мог получить этот номер, то есть подключение идёт **к
    существующему серверу**.

    Отсюда два следствия. Первое, практическое: замер при чужом экземпляре
    недостоверен — «текущая страница» может принадлежать чужому проекту, и числа
    будут не про нашу модель. Поэтому перед серией живых прогонов надо убеждаться,
    что `mmain.exe` не запущен. Второе, про владение: `owned_pid` **не является
    доказательством владения** — при присоединении он чужой по определению, и
    убийство по нему снесло бы чужую сессию. Проверка `owned_pid not in before`
    в `probe_client` — не формальность, а именно тот сенсор, который это ловит,
    и в этот раз он сработал дважды подряд, отказавшись работать.

Порядок работы был: **1 → 2 → 3 → 4** (по прежней нумерации). Первый шаг
выполнен (PR #15) — риск потери пользовательских данных закрыт. Второй выполнен
в `simintech-code` (жизненный цикл расчёта моста); при его разборе добавился
новый пункт про контракт отказа, он поставлен сразу за ним. Четвёртый —
адресация портов — закрыт 2026-09-23 (PR #18), и тем же прогоном найден
пункт 6 — неполный диагностический контракт, закрытый в PR #19. **Остаётся
охват типов** (пункт 5), и он идёт последним сознательно: расширять фильтр
раньше, чем у моста появится независимый признак причины отказа, значило бы
получить более точную адресацию портов при менее честном объяснении неудачи
расчёта — то есть променять один недоказанный шаг на другой.

Эта запись намеренно находится здесь, а не в закрытом PR: найденный дефект должен
оставаться видимым после merge и служить входом для следующих задач. Поэтому

допущениями, которые переживают исправление.

## 7. Расширение MCP-слоя: проверка параметров, ресурсы, работа без COM (2026-09-16)

Пять пунктов из списка предложений по `simintech-mcp` сделаны; один отклонён по
техническим причинам, ещё один требует Windows.

| Что | Как сделано |
|---|---|
| Проверка параметров блоков | `_check_params` сверяет имена с каталогом **до** записи. Неизвестное имя и запись в вычисляемый параметр (`mode 0`) — отказ `isError`; в тексте — список известных имён и способ обхода (`allow_unknown`). В `add_block` проверка идёт **до** создания блока: отказ не оставляет блок на схеме. Класс вне каталога («Класс-которого-нет-в-каталоге») не проверяется, но об этом сообщается |
| Ресурсы MCP | `simintech://blocks/catalog` — классы, имена параметров, пометка вычисляемых; `simintech://skills` и `simintech://skills/<имя>` — список и текст скиллов |
| Интеграция со скиллами | Скиллы читаются из `simintech-skill` по `SIMINTECH_SKILLS_DIR` (иначе — соседний checkout). Хранить их здесь не нужно: репозиторий скиллов остаётся источником истины |
| Временные ряды из результатов | `summarize_output_file` — сводка по колонкам файла блока «В файл»: точки, диапазон времени, min/max/среднее, средний наклон |
| Работа без COM (Linux) | `inspect_project_file` разбирает сохранённый `.xprt`: классы, параметры, вычисляемые имена, имена блоков. Тот же инструмент — ревью модели без запуска среды |
| Логирование | `SIMINTECH_MCP_LOG` включает JSON-строки о каждом вызове (имя, аргументы, длительность, исход) в stderr или файл |

Общее для новых возможностей:

- **Песочница одна.** `summarize_output_file` и `inspect_project_file` разрешают
  путь тем же `_resolve_output_path`, что и `read_output_file`: файл должен
  лежать в каталоге результатов. Отдельного «читать что угодно по пути от
  клиента» инструмента нет — иначе ограничение обходилось бы через соседний
  инструмент.
- **Контракт отказа общий.** Инструменты без COM идут под `_plain_tool` — это
  тот же `_call_guarded` и тот же `ToolError`, только без перехода в COM-поток.

### 7.1. Отклонено: пул потоков и параллельные COM-вызовы

Предложение «добавить пул потоков, чтобы длительные расчёты не блокировали
сервер» выполнено быть не может — и пул уже есть. `_COM_EXECUTOR` объявлен с
`max_workers=1` намеренно: COM-объект принадлежит апартаменту создавшего его
потока, и обращение из другого потока даёт `CO_E_OBJNOTCONNECTED` (проверено на
реальном SimInTech, §6.1). Увеличение числа рабочих потоков не ускорит работу, а
сломает её. Асинхронная обёртка тоже ничего не даёт: FastMCP и так выполняет
синхронные инструменты вне цикла событий транспорта.

Что действительно можно сделать при необходимости: не держать `run(to_time=…)`
на одном вызове, а возвращать управление сразу и опрашивать `get_time` — это
изменение сценария, а не параллелизма.

### 7.2. Найдено попутно: пин зависимости был нерабочим

`pyproject.toml` ссылался на тег `v0.2.0`, где нет `standard_block_size` и
`default_output_dir`. Сервер импортирует их на уровне модуля, поэтому **на
чистой установке он не запускался вообще** — `ImportError` при импорте, до
любого COM. Локально это не проявлялось: библиотека стояла из checkout.

Пин был переведён на коммит библиотеки, содержащий нужные API. **Завершено
2026-09-18:** выпущен тег `v0.3.0` (коммит `a2daa1c`, `__version__ = "0.3.0"`),
и пин закреплён на этом коммите.

**Обновлено 2026-09-21:** пин переведён на `13415c5` — merge-коммит PR #11 со
скриптовым мостом. Тег `v0.3.0` для этого не годится: он указывает на
`a2daa1c`, где моста ещё нет. Это тот же урок с другой стороны — «самый свежий
тег» не значит «нужный код», и проверять надо содержимое коммита, а не имя
ссылки.

На тег пин сознательно **не** переводится, хотя тег и указывает на тот же
коммит. Причина — изменяемость: `refs/tags` можно передвинуть, и та же строка
зависимости начнёт разрешаться в другой код молча. Это не теория: в проекте уже
случался обратный случай, когда тег `v0.2.0` стоял на `44c6af7` с
`__version__ = "0.1.0"` — на коде, от которого пин как раз и защищал, — а
выглядел при этом новее библиотеки. SHA не переписать, поэтому закрепляет он.

Урок, который стоит держать в голове и после этого: **тег нельзя брать ни по
имени, ни по факту существования.** Перед сменой пина проверять, что коммит
несёт нужное: `git show <sha>:simintech_api/__init__.py` даёт ожидаемую
`__version__`, а `standard_block_size` и `default_output_dir` в нём есть.

### 8.3. Отклонено сознательно

- **Контейнер внедрения зависимостей (`dependency-injector`) и `Protocol` над
  COM-клиентом.** Абстракция без второго потребителя: реализация COM одна, а
  тесты обходятся подменой состояния сессии и фейками — они уже работают без
  COM и без библиотеки. Второй реализации не появится: эмуляция COM на Linux
  не нужна, потому что без COM-инструментов в сервере нет.
  Когда появится настоящий второй бэкенд — тогда и абстракция.
- **Паттерн «Стратегия» для расстановки блоков.** В `layout/` два модуля —
  `placer` и `router` — и по одному алгоритму в каждом. «Стратегия» с одной
  стратегией добавляет слой, ничего не заменяя; выбор появится вместе со
  вторым алгоритмом.
- **Параллелизм COM** — см. §7.1: невозможен, а не отложен.
- **Песочница для `save_project`/`open_project`.** Автоматический разбор
  безопасности находит «запись и открытие файла без песочницы» и предлагает
  прогнать путь через тот же помощник, что у чтения. Это отклонено: сохранить
  модель и открыть проект **по указанному пользователем пути** — назначение
  этих инструментов, и песочница сломала бы их (модель нельзя вынести за
  каталог результатов). Содержимое при этом не произвольно — его сериализует

### 10.2. Подтвердилось, но причина глубже, чем в разборе

**Полнота снимка топологии (пункт 6 разбора).** Разбор перечисляет шесть
равновероятных причин пустого результата. Настоящая дыра уже́ и хуже:
`objcnt = getobjcount(contid)` (`topology.py:340`) считается и используется
**только как граница цикла** (`:343`, `:353`, `:373`). В результат он не
попадает: проба пишет ровно три вида строк — `object` (`:347`), `port`
(`:365`), `conn` (`:392`) — и ничего больше. Значит контейнер, вернувший не тот
id, даёт **валидную пустую `Topology`** без единого признака снаружи.

Фильтр читает только типы 100 и 102 (`:346`), и это осознанное решение:
расширение списка требует отдельного доказательства, поэтому 104 «В память» и

предполагаемыми (`:303-308`). То есть **потери есть по замыслу** и снаружи
неотличимы от отсутствия связей. Envelope нужен не против гипотетического
сбоя, а чтобы сделать уже существующий фильтр видимым вызывающему — это более
сильное обоснование, чем в разборе.

- **«Обновить пин» первым пунктом P0.** Смена пина инертна для поведения: MCP к

### 10.6. Правило, к §9.3

Разбор, написанный по поиску, и разбор, написанный по коду, дают **разные
ошибки**. Первый верно видит структуру и неверно — глубину: он называет
симптомы («нет доказательства полноты», «теряется provenance»), не находя
строки, где потеря сделана намеренно. Второй тонет в деталях и теряет картину.

Практический вывод для следующих аудитов: структурные выводы можно принимать
сразу, а любой пункт вида «этого нет» или «это сломано» — только с указанием
файла и строки. Без строки это гипотеза, и проверять её дешевле, чем
планировать по ней работу.

### 10.7. Решение о остановке в read-only инструменте

В пункте 2 этого раздела остался открытым вопрос: не должен ли MCP-инструмент
чтения топологии **сам** останавливать расчёт. Решение: **не должен.**

```
model_topology() → проект не остановлен
                   → ERROR: чтение модели требует остановленного состояния
simulation_stop()  ← отдельный инструмент, вызывает агент
```

Обоснование не вкусовое, а из уже названного дефекта: GUI-эффект
`save_project` по умолчанию признан здесь плохим именно потому, что read-only
по смыслу операция меняла состояние среды. Тихая остановка расчёта — то же
самое, но дороже: агент может не знать, что расчёт вообще шёл, а расчёт
чужой — единственное, что проба уничтожает безвозвратно.

Управление жизненным циклом остаётся у агента; инструмент только сообщает, что
условие не выполнено. Отказ при этом обязан быть **отличимым**: отдельный тип
для «не остановлен» против «состояние не читается», иначе агент не поймёт,
останавливать ему или разбираться с чтением состояния.

### 10.9. Зелёный CI не является гейтом слияния

Проверено по API 2026-09-22: во всех трёх репозиториях защита ветки `main`
включена и требует **одобрения ревью** (устаревшие одобрения снимаются), но
`required_status_checks` — **`null`**. Значит `check` в PR — информационный:
слить можно с красным CI, если кто-то поставил одобрение; `enforce_admins`
тоже выключен.

Для проекта, который отдельно оговаривает, что «проверка, не способная
покраснеть, — не проверка», это дыра того же рода на уровне настройки
репозитория: гейты есть, а гейтом не являются.

**Исправление названо точно (проверено 2026-09-23).** У всех трёх репозиториев
в PR ровно одна проверка, и имя у неё одно и то же — `check`; значит джоба
однозначна и гадать не о чем. На каждый репозиторий:

```bash
gh api -X PATCH repos/producedbysavant/<repo>/branches/main/protection \
  -f 'required_status_checks[strict]=true' \
  -f 'required_status_checks[contexts][]=check'
```

### 10.11. Владение дескриптором `fid`: scope-gate и правка (2026-09-24)

Пункт 11 решён не догадкой: сначала замер, потом правка. Ветка
`fix/script-bridge-fid-ownership` от `ec9dadd`, PR `simintech-code` **#22**.

**Scope-gate — сначала вопрос, а не правка.** Одиннадцать живых вариантов, каждый
на своей копии демо; оракул из трёх свидетельств (пара маркеров и строка после
чужого вызова в файле моста; созданный и заполненный файл чужака; числовое
значение дескриптора до и после). Про язык измерено:

| # | Что измерялось | Результат |
|---|---|---|
| 1 | пустые скобки в заголовке процедуры | ошибка компиляции — два независимых контроля |
| 2 | вложенная процедура и переменные охватывающего блока | **видит и изменяет** — это и есть канал вреда |
| 3 | тень имени внутри процедуры | разрешена |
| 4 | тень имени во вложенном блоке | **запрещена** |
| 5 | параметр процедуры | копия |
| 6 | строковый параметр | работает |

Правила 2–4 закрывают вопрос: **отдельной области видимости под дескриптор у
языка нет** — локальные объявления защищают только объявленное локально, тень
блока отвергается компилятором. Правило 5 изоляцию не даёт по другой причине:
чужой код обращается к внешнему имени `fid`, а не к нашему параметру. Осталась
недостижимость по имени — то есть довод «имя, которого чужой текст не знает».

**Матрица владения (живой стенд).** Общий `fid`: маркеров **1/0**, дескриптор не
пережил чужой вызов, строки после вызова в файле моста нет. Своё имя моста плюс
приманка: **1/1**, дескриптор до и после совпал, строка есть. На **настоящей**
вендорской процедуре — то же самое, причём её JSON в обоих контрактах одного
размера (46 135 байт): процедура выполняется одинаково, меняется только то,
переживает ли вызов дескриптор моста.

**Правка.** Дескриптор моста — под именем `br_result_<метка запуска>` (метка
случайна и до запуска проверяется на отсутствие в проекте), `fid` — приманка,
связанная с дескриптором, `br_writeln` — запись после чужого захвата. Приманка
объявлена намеренно: без неё вендорский скрипт не компилируется, расчёт молча не
пойдёт, и проба не выполнится вовсе.

**Обязательная мутация поставлена вручную.** Маркеры возвращены на общее `fid`,
всё остальное в шаблоне не тронуто: живой тест краснеет с диагнозом «в результате
нет ровно одной пары маркеров» — ловится потеря владения, а не пропавшая
процедура; юнит-стражи краснеют вдвоём. Более грубая мутация (шаблон без
`br_writeln`) тоже краснеет, но как ошибка компиляции — поэтому и взята острая.

**Гейты.** 551 unit (единственный красный, `test_pak`, предсуществующий —
проверено на базе без правок), flake8, mypy ×2, живой набор **23 passed** за
4 мин 40 с, включая сверку с эталоном вендора: топологический контракт не
сдвинулся.

**Замер дважды был неверным, и оба раза это поймано, а не умолчано.** Первый
прогон дал шесть красных из восьми, и все красные отличались от зелёных
заголовком процедуры с пустыми скобками: вывод про язык проверен бисектом, где
варианты различаются **только** заголовком, а не принят за результат. Первая
мутация оказалась не мутацией — сборщик оставлял мосту неповторяемое имя, а
приманку не объявлял, поэтому красное означало ошибку компиляции, а не захват
дескриптора; мутация переставлена на одну подстановку — пути записи маркеров.

**Не тронуто:** тип 111, оставшиеся continuation-paths, семантика первого соседа.

### 10.16. Milestone 4, первый срез: структуры и `model_overview` (PR #23)

**Что решено в коде, а не в тексте.** Слой **не делает собственных COM-вызовов** —

### 10.19. M4.6 «связи пары», ревизия хвостов и остатки в ветвях (2026-09-26)

**Срез M4.6 собран** — ветка `feat/semantic-query-connections` в `simintech-code`
(`fe60820`, от текущего `main`): `query_connections` отвечает на
вопрос «какие связи идут между этими двумя объектами». **Новых COM-вызовов нет** —
отбор по уже прочитанному обзору.

**Что решено в коде.** Отвечает **связями, а не соседями**: у каждой связи названы
оба конца, поэтому у пары видно каждую пару портов, а не «ещё одного соседа».
Порядок в вопросе не значит ничего (`(A, B)` и `(B, A)` — один вопрос), а `links`
остаются в порядке разбора. Адрес — имя объекта, а не пара (имя, индекс): индексы
портов видны в самих связях. Связь объекта с самим собой спрашивается тем же
вызовом и **не** смешивается со связями с соседями. Отказы проверяют **оба**
названных конца, а отсутствие связи — не отказ, а обычное состояние модели
(`links == []`). Форма связи одна на все ответы: обзор и запрос используют общий
`_connection_to_dict`, и тест сверяет совпадение форм; инвариант с досмотрами
закреплён в обе стороны.

**Гейты:** 607 unit, `flake8`, `mypy` ×2 (19 файлов), живой набор — 32 теста (7 в
семантическом файле, из них два новых). Мутации: **5 из 5 краснеют** (порядок
концов, проверка второго конца, отказ на пустой паре, пересечение вместо равенства,
своя форма связи).

**Грабля живого набора, всплывшая при прогоне.** Полный набор в «естественном»
порядке даёт **1 passed, 31 skipped за 13 с**: первым идёт `test_connect_disconnect`,
он поднимает собственный клиент и завершает его не мгновенно, а сессионная фикстура
видит этот процесс как чужой и пропускает остальные тесты (та же грабля, что в
§10.18, но теперь воспроизводимая). Зелёный набор получается, если файлы идут так,
чтобы фикстура создалась до него: `semantic → topology → lifecycle` — 27 passed за
6 мин 18 с, плюс `script_bridge_live` — 32. Кандидат на лечение: дать фикстуре
отличать процесс, порождённый тестами **этого же** прогона, вместо опоры на порядок
файлов.

**Процессы после прогонов проверялись верным источником** —
`get_mmain_pids()`, а не грепом `tasklist` (см. поправку выше): во время прогона
виден один процесс — свой, после прогона ноль.
